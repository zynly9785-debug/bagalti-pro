# بقالتي برو — إصدار Capacitor الهجين 1.4.5

هذا المجلد هو إصدار Android المبني بـ React وCapacitor، ويحتفظ بقاعدة SQLite/SQLCipher محلية مع مزامنة سحابية متعددة المتاجر عبر Supabase. لا تضع أي مفتاح `service_role` داخل التطبيق أو ملف البيئة الخاص بالبناء.

## إعداد البناء

1. استخدم Node.js 24 أو أحدث وAndroid SDK/JDK المتوافقين مع Gradle wrapper.
2. نفّذ `npm ci --legacy-peer-deps`.
3. انسخ `.env.example` إلى `.env.local` وأدخل `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` فقط.
4. نفّذ `npm run build` ثم `npx cap sync android`.
5. لبناء APK تجريبي: `cd android && ./gradlew assembleDebug`. الملف الناتج في `android/app/build/outputs/apk/debug/app-debug.apk`.

## إصلاح قاعدة البيانات 1.4.1

يعالج هذا الإصدار خطأ `Already in transaction` عند التهيئة والحفظ: دوال `run()` و`execute()` في إضافة Capacitor تبدأ معاملة تلقائياً بشكل افتراضي. كل عمليات الكتابة التي تقع داخل معاملة خارجية تستخدم الآن `transaction=false` كي تشارك في المعاملة نفسها بدلاً من بدء معاملة متداخلة. لا يمسح الإصلاح قواعد بيانات موجودة ولا يعيد ضبط مفتاح التشفير.

## تسجيل الدخول دون OTP

واجهة التاجر تقبل رقم الهاتف وكلمة المرور، ويحوّل التطبيق الرقم داخلياً إلى عنوان alias غير مخصص لتلقي البريد لتسجيل Supabase Auth بالبريد/كلمة المرور. يبقى رقم الهاتف الحقيقي محفوظاً في metadata وملف المتجر ويظل هو ما يراه المستخدم. إعداد Phone/SMS المباشر غير مفعل لأن مزود SMS ومفاتيحه غير مهيأة؛ لذلك لا يُرسل OTP.

هذا الاختيار يعني أن Supabase لا يتحقق من ملكية رقم الهاتف. لا تمنح أي حساب صلاحية `platform_owner` اعتماداً على الرقم وحده؛ افحص الحساب الذي أنشأه المالك بنفسه من لوحة Supabase ثم امنحه الدور إدارياً. لا توجد حالياً حسابات تجريبية مضافة إلى قاعدة البيانات.

بوابة مالك التطبيق تستخدم Edge Function `owner-sign-in-by-phone`: تبحث عن رقم الهاتف المسجل في `profiles`، ولا تسمح إلا بدور `platform_owner`، ثم تتحقق من كلمة المرور على بريد حساب Supabase الحقيقي بواسطة Auth. لذلك يعمل حساب المالك المنشأ ببريد عادي مع إدخال رقم الهاتف في التطبيق، من دون تغيير بريد الحساب أو تخزين كلمة المرور في قاعدة البيانات أو التطبيق.

## قاعدة البيانات والمزامنة

- يحتفظ التطبيق بالعمليات التجارية محلياً، ويمكن البيع دون اتصال.
- على Android، تُحفظ بيانات المتجر في SQLite/SQLCipher الأصلي، بما فيها الفواتير والسداد والدفتر المالي والورديات؛ نسخة المتصفح تستخدم تخزين المتصفح للتطوير فقط.
- عند الاتصال، يسحب أحدث `sync_records` أولاً ويُبقي النسخة ذات الطابع الزمني الأحدث قبل رفع السجلات المحلية الأحدث.
- سياسات RLS تعزل سجلات المتاجر، وتُدار حالة الاشتراك من جدول `stores` ووظيفة الإدارة المقيدة.
- migration `phone_auth_alias_profile` تحفظ رقم الهاتف الوارد في بيانات الحساب داخل `profiles`.
- زر «نسيت كلمة المرور؟» يفتح خيارات اتصال/SMS/WhatsApp للدعم. إعادة تعيين كلمة مرور التاجر من لوحة المالك تمر عبر Edge Function `admin-reset-store-password` المحمية بجلسة JWT ودور `platform_owner`، وتُسجل في `admin_security_events`.
- لا تضع كلمات مرور أو أرقام هوية أو إجابات استرداد ثابتة داخل APK. لا يوجد OTP عند إعداد الدخول الحالي، لذلك لا يكفي رقم الهاتف وحده لإثبات ملكية الحساب أو منح صلاحيات المنصة.
- اقتران الطابعات الحرارية يتم من إعدادات Bluetooth في Android، ثم يختار التطبيق جهازاً مقترناً يدعم Bluetooth Classic SPP لإرسال الإيصال.

## قبل التوزيع العام

يُنتج GitHub Actions نسخة `debug` للتحقق فقط. لن ينشر رابط تنزيل دائم إلا بعد إضافة أسرار التوقيع التالية إلى إعدادات Actions في المستودع:

- `ANDROID_SIGNING_KEY_BASE64`: محتوى ملف keystore بترميز Base64.
- `ANDROID_KEY_ALIAS`
- `ANDROID_STORE_PASSWORD`
- `ANDROID_KEY_PASSWORD`

يبني سير العمل نسخة `release` موقعة بالمفتاح نفسه، ويرفعها إلى GitHub Releases باسم `BaqalatyPro.apk`. بعد نجاح أول نشر موقّع، يكون رابط التنزيل الدائم:
`https://github.com/zynly9785-debug/bagalti-pro/releases/latest/download/BaqalatyPro.apk`

لا ترفع ملف keystore إلى GitHub ولا تغيّر المفتاح بعد النشر؛ المفتاح نفسه مطلوب لكل تحديث حتى يثبت Android التطبيق فوق النسخة السابقة. اختبر التسجيل، إعادة تسجيل الدخول، البيع دون اتصال، المزامنة بعد عودة الشبكة، واستعادة نسخة SQLite على جهاز Android فعلي.
